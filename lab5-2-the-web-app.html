2. The Calculator Web App

🎯 Why this step? You cannot automate what you do not understand. Five minutes reading the project tells you the order of your pipeline: what each stage needs, and what it produces for the next one.

The project is in the teacher's template repository, in lab5/calc-web. Open it now in a new tab and keep it open while you read this page:
📂 github.com/nouhakhyari-sys/jenkins-labs-template/tree/main/lab5/calc-web

You do not copy or download anything: your pipeline clones this repository by itself at every build, like the checkout of Lab 4. You only read the files here.

FileRole
src/Calculator.javaThe calculator of Labs 3 and 4 (with the SIMULATE_BUG switch).
src/CalculatorServer.javaA tiny web server on port 8080: / shows the version, /add/2/3 answers 5.
test/CalculatorTest.javaUnit tests: the calculator alone, no server, no network.
test/ServerTest.javaIntegration tests: start the server and call it over HTTP, like a user. The web layer and the calculator working together (see the box below the table).
DockerfileHow to build the image of the application.
🔎 Integration test? There is no database here. True: in this project, integration means the parts of our own app working together. The app has two layers:
  1. The calculator logic (Calculator.java): add(2, 3).
  2. The web layer (CalculatorServer.java): it opens a port, reads the address /add/2/3, takes out 2 and 3, calls the calculator and sends 5 back over HTTP.

CalculatorTest checks layer 1 alone. ServerTest checks layers 1 and 2 together, through the real network: a real server, a real HTTP request, a real answer. A bug in the web layer (wrong address, server not starting) is caught only by ServerTest, even when the calculator is correct. Some teams call this an API test.

In a real project, integration tests also include external components: a database (MySQL), a message queue, another service, often started in Docker containers by the pipeline itself.

The Dockerfile, line by line

lab5/calc-web/Dockerfile (comments removed)
FROM eclipse-temurin:21-jre
ARG APP_VERSION=dev
ENV APP_VERSION=${APP_VERSION}
WORKDIR /app
COPY build/calculator-web.jar app.jar
EXPOSE 8080
CMD ["java", "-jar", "app.jar"]

Before reading the explanation, try to say what each line does. Then check:

Show the explanation of each line
  • FROM eclipse-temurin:21-jre: start from an image that already has Java 21. A precise tag, not latest, so the build is reproducible (slide Docker Run: tags).
  • ARG / ENV APP_VERSION: Jenkins gives the version when it builds the image; the app shows it on its home page.
  • WORKDIR /app: the folder inside the image where the next commands work.
  • COPY build/calculator-web.jar app.jar: copies the jar from your workspace into the image. The jar must already exist.
  • EXPOSE 8080: documents that the app listens on 8080 inside the container. It does not open any port on your computer: that is the job of -p.
  • CMD: the command the container runs when it starts. The container lives as long as this command runs.

✅ Checkpoint 2: answer in report.txt, in your own words (one or two lines each).
  1. Which file does the Dockerfile need that is not in Git? Which stage creates it?
  2. Which test file is a unit test, which one an integration test? What is the difference?
See the answer
  1. The jar, build/calculator-web.jar: the line COPY build/calculator-web.jar app.jar needs it. It is not in Git, because it is built, not written by hand (the build/ folder is in .gitignore). The Package stage creates it, with jar cfe ….
  2. CalculatorTest is a unit test: it tests the calculator alone, with no server and no network; it is fast. ServerTest is an integration test: it starts the web server and calls it over HTTP, like a user, so it checks the web layer and the calculator together. It is slower, but it finds problems a unit test cannot see (wrong address, wrong answer format, server not starting). There is no database here: the integration is between the parts of our own app and the network.
