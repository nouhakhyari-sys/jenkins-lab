Lab 5 · Deploy with Docker

3. Build, Test and Package

🎯 Why this step? Tests are the gate of CI: nothing goes further if they fail. Unit tests are fast; integration tests are slower (they start a server). Running them at the same time gives the developer the answer sooner. A parallel block is the Jenkins version of two GitHub Actions jobs without needs.

Create a Pipeline job named calc-web. In Pipeline › Definition, keep Pipeline script and paste the script for your Jenkins (Docker or Windows). It is almost complete: two lines marked // TODO in the Tests stage are for you. Fill them in with the guide below the script, then click Save.

Part A, to complete (Jenkins in Docker)
pipeline {
    agent any

    options {
        timestamps()
    }

    parameters {
        booleanParam(name: 'SIMULATE_BUG', defaultValue: false,
                     description: 'Tick to put a bug in the calculator')
    }

    stages {
        stage('Checkout') {
            steps {
                dir('app') {
                    git url: 'https://github.com/nouhakhyari-sys/jenkins-labs-template.git', branch: 'main'
                }
            }
        }
        stage('Build') {
            steps {
                dir('app/lab5/calc-web') {
                    sh 'javac --release 21 -d build/classes src/*.java test/*.java'
                }
            }
        }
        stage('Tests') {
            parallel {
                stage('Unit tests') {
                    steps {
                        dir('app/lab5/calc-web') {
                            sh "java -DsimulateBug=${params.SIMULATE_BUG} -cp build/classes CalculatorTest"
                        }
                    }
                }
                // TODO 1: a second stage 'Integration tests' that runs ServerTest
            }
            post {
                always {
                    // TODO 2: publish the XML reports of build/test-results (both test stages)
                    archiveArtifacts artifacts: 'app/lab5/calc-web/build/test-results/*.xml'
                }
            }
        }
        stage('Package') {
            steps {
                dir('app/lab5/calc-web') {
                    sh 'jar cfe build/calculator-web.jar CalculatorServer -C build/classes .'
                }
                archiveArtifacts artifacts: 'app/lab5/calc-web/build/calculator-web.jar', fingerprint: true
            }
        }
    }

    post {
        always {
            cleanWs()
        }
    }
}

✍️ Your turn: fill in the two TODOs

Everything you need is already on your screen: the Unit tests stage just above the TODOs, and what you learned in part 2 and in Lab 3.

TODO 1: the Integration tests stage

In part 2 you saw that the project has two test classes: CalculatorTest (unit) and ServerTest (integration). The script already runs the first one, in this stage:

The Unit tests stage, already in your script (Windows: bat instead of sh)
stage('Unit tests') {
    steps {
        dir('app/lab5/calc-web') {
            sh "java -DsimulateBug=${params.SIMULATE_BUG} -cp build/classes CalculatorTest"
        }
    }
}
  1. Copy this whole block, from stage( to its last }.
  2. Paste it in place of the line // TODO 1 … (still inside parallel { }).
  3. In the copy, change two things: the stage name (Unit tests → Integration tests) and the class to run (CalculatorTest → ServerTest).

Two stages inside parallel { } = two tests running at the same time.

TODO 2: publish the test reports

Each test class writes an XML report. In Lab 3, the junit step read these reports to show Test Result and to make the build yellow when a test fails. Its form is junit 'path/to/the/reports/*.xml'.

Build the path in two pieces:

  1. The project folder. The tests ran inside dir('app/lab5/calc-web'). But post is outside that dir(), so the path must start with that folder.
  2. The reports. Inside the project, the tests write in build/test-results/ (the table of part 2: "test reports (XML)"). *.xml takes the two files at once.

So the line you write in place of // TODO 2 … is:

TODO 2: fill the blank
junit '____________________/build/test-results/*.xml'

Fill the blank with the project folder, then click Save. Clue: the line just under TODO 2 already uses this path. It archives the same XML files as artifacts, like in Lab 3, so you will find them next to the jar on the build page.

Why fill both before running? Jenkins checks the whole script before it starts, so an incomplete script can be refused. And without TODO 2, no test report is published: no Test Result, and no yellow build when a test fails.

🔮 Predict first. Write your answer down before you run, then compare.
  1. Without the bug: how many tests will Jenkins report, and how many stages will you see side by side?
  2. With SIMULATE_BUG ticked: will the build be red or yellow? Will the Package stage run?

Run and observe

  1. Build with Parameters, SIMULATE_BUG unticked. See the parallel branches in Blue Ocean: open http://localhost:8080/blue (type /blue after the Jenkins address), click the calc-web pipeline, then click the row of your run. In the graph, Tests splits into two branches, one above the other: Unit tests and Integration tests. Click a branch to see its logs only. (No Blue Ocean on your Jenkins? Open the run in the classic interface › Pipeline Overview: same graph.)
  2. Back in the classic interface (exit icon at the top right of Blue Ocean), open the run › Test Result: how many tests?
  3. Open the Console Output: the lines of the two stages are mixed, each starting with [Unit tests] or [Integration tests]. They ran at the same time.
  4. Run it with SIMULATE_BUG ticked. In Blue Ocean, open this run: which branch shows failing tests? Compare with your predictions.
Show the explanation
  • Without the bug: green, 7 tests (4 unit, 3 integration), two stages in parallel: the Tests stage lasts as long as the slowest one, not the sum.
  • With the bug: both stages find it (the server uses the same calculator). The test programs report the failures in their XML instead of crashing, and junit marks the build yellow (UNSTABLE): "it built, but tests fail". Red means the pipeline itself broke (compilation error, missing file). The next stages still run: Package does too. Part 4 adds the rule that stops a yellow build from becoming an image.
  • junit is in the post of Tests, after both parallel stages, so one call collects the two reports, even when a test failed (always).
⚠️ The classic Stage View table on the job page cannot draw parallel stages: it shows Tests, Unit tests and Integration tests as columns one after the other, as if they ran in sequence. Use Blue Ocean (or Pipeline Overview) to see them in parallel.
Take a screenshot of the Blue Ocean graph (or Pipeline Overview) with the two parallel branches visible: it is part of your hand-in (stages.png).
✅ Checkpoint 3: answer in report.txt, in your own words (one or two lines each).
  1. Unit and integration tests run in parallel. What do you gain? Why is junit placed after both of them, not inside each?
  2. With SIMULATE_BUG, which stage(s) failed, and why is the build yellow and not red?
See the answer
  1. Time. The two test classes run at the same time, so the Tests stage lasts as long as the slowest one, not the sum of both: the developer gets the answer sooner. In a real project with 10 minutes of unit tests and 20 minutes of integration tests, that is 20 minutes instead of 30.
    junit after both. It is in the post { always { } } of the Tests stage, so it runs once, after both branches, and *.xml collects the two reports together. always means it runs even when tests fail: that is exactly when you need the report.
  2. Both test classes found the bug: Test Result shows 3 failing tests, 2 in CalculatorTest (unit) and 1 in ServerTest (http_add_2_and_3), because the server uses the same wrong calculator.
    Yellow, not red: no stage crashed. The test programs ran to the end and wrote the failures in their XML reports; junit read them and marked the build UNSTABLE (yellow) = it built, but tests fail. Red (FAILURE) means the pipeline itself broke: a compilation error, a missing file, a command that fails.
