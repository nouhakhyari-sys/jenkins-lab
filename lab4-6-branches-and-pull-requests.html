Lab 4 · Freestyle Projects and Blue Ocean

6. Branches and Pull Requests

The job Blue Ocean created is not a simple Pipeline job like in Lab 3: it is a multibranch pipeline. Jenkins watches your whole repository and creates one pipeline per branch, and one per pull request, by itself. This is GitHub Flow (chapter 3) in action: every change is tested before it is merged into main.

Why not a webhook? With a webhook, GitHub would call Jenkins at every push. But your Jenkins is at localhost: GitHub, on the Internet, cannot reach it. So Jenkins does the opposite: it scans GitHub regularly and builds what is new. You set this scan to every minute.

Step 1: Scan GitHub every minute

  1. Click Go to classic (arrow icon, top right of Blue Ocean). Blue Ocean created a job named after your repository (for example jenkins-labs).
  2. Open this job, click Configure, and in the left menu click Scan Repository Triggers.
  3. Tick Periodically if not otherwise run, choose the interval 1 minute, and Save.

Step 2: Create a branch from Blue Ocean

  1. Back in Blue Ocean, open your pipeline and click the pencil icon (Edit) to open the editor on main.
  2. Click the + after Package, add a stage Hello with a script step: echo Hello from feature/hello (same in Docker and Windows).
  3. Click Save. Description: Add Hello stage. This time choose Commit to new branch and type feature/hello. Click Save & run.
  4. Open the Branches tab: feature/hello has its own pipeline, with the Hello stage. main does not have it.

Do not look for the Git branches in the graph. The graph shows the stages of one run of one branch: its fork is the parallel block (Test and Java version), not a Git branch. The Git branches are listed in the Branches tab, one line (one pipeline) per branch.

Step 3: Open a pull request

  1. On GitHub, open your repository. GitHub suggests Compare & pull request for feature/hello: click it, then Create pull request (base: main).
  2. Back in Blue Ocean, wait one minute (the scan) and open the Pull Requests tab: your pull request is there, built automatically. Jenkins built the code as if it were merged into main, to check that the merge does not break anything.
  3. Go back to the pull request page on GitHub: it now shows All checks have passed, and a green ✓ next to the commit. This check comes from Jenkins: after building the pull request, Jenkins sent its result back to GitHub. Click the ✓ to see its name (continuous-integration/jenkins/…). This is how a team sees, before merging, that the change is safe.
  4. Take a screenshot of the Pull Requests tab in Blue Ocean: it is part of your hand-in (pull-request.png).

Step 4: Merge

  1. On GitHub, click Merge pull request, then Confirm merge.
  2. Within a minute, Jenkins builds main again: the run now has the Hello stage. Open its Changes tab: this time it is not empty, it lists the commit Add Hello stage.

Questions

1. Who started the builds of feature/hello, of the pull request and of main after the merge?

Nobody clicked Build: Jenkins started them after its scan of GitHub found something new (Blue Ocean also started the first run of the branch when you saved). With a webhook, GitHub would have called Jenkins at once; the scan does the same job, with up to one minute of delay.

2. After you opened the pull request, feature/hello may have disappeared from the Branches tab. Why?

By default, Jenkins builds a branch that has an open pull request as a pull request, not twice. It moves to the Pull Requests tab. After the merge (or if you close the pull request) it can come back as a branch.

3. Why is it useful to build a pull request before the merge?

The team sees whether the change breaks the build or the tests before it reaches main. main stays always green and ready to deploy: this is GitHub Flow, and the reason teams require a green build before allowing a merge.

4. Compare with Lab 3. What did the Pipeline job my-java-pipeline do with other branches?

Nothing: a Pipeline job builds one branch (main), when you click. A multibranch pipeline discovers every branch and pull request with a Jenkinsfile and builds each of them on its own.
