Lab 6 · Distributed Builds with Agents

2. A Linux Agent in a Docker Container

🎯 Why this step? An agent is any machine that runs agent.jar, a small Java program that connects to the controller and runs the steps it receives. The official image jenkins/inbound-agent is a Linux machine with Java 21 and agent.jar ready: one docker run and you have a Linux build machine, even on Windows.

A. Create the node in Jenkins

  1. Manage Jenkins › Nodes › New Node. Node name: linux-agent. Type: Permanent Agent. Create.
  2. Fill in the form:
    FieldValueMeaning
    Number of executors22 builds at the same time on this agent
    Remote root directory/home/jenkins/agentThe folder where workspaces are created, on the agent
    Labelslinux javaWhat this agent can do. Two labels, separated by a space
    UsageOnly build jobs with label expressions matching this nodeIt only takes jobs that ask for one of its labels
    Launch methodLaunch agent by connecting it to the controllerThe agent will call Jenkins
  3. Use WebSocket: depending on your Jenkins version, this box is under Launch method › Advanced, or not shown at all. You do not need it: the start command of the agent (step B) already contains JENKINS_WEB_SOCKET=true, and that is what makes the agent use WebSocket. If you see the box, tick it: the commands on the node page then include -webSocket.
  4. Save. The node appears with a red cross: it exists, but no machine is connected yet.
  5. Click linux-agent. Jenkins shows the commands to connect it. In them, find the secret: a long string of letters and digits after -secret. Copy it.
🔑 The secret is the password of this agent. Anyone who has it can connect a machine called linux-agent and receive your code and your credentials during builds. Do not put it in Git or in a screenshot.

B. Start the agent container

Docker Desktop must be running (Engine running, bottom left), and Jenkins must open on http://localhost:8080.

In PowerShell (or a terminal), run this one line, after replacing PASTE_THE_SECRET_HERE with your secret:

Start the Linux agent (one line)
docker run -d --name linux-agent --init --add-host=host.docker.internal:host-gateway -e JENKINS_URL=http://host.docker.internal:8080 -e JENKINS_SECRET=PASTE_THE_SECRET_HERE -e JENKINS_AGENT_NAME=linux-agent -e JENKINS_WEB_SOCKET=true -e JENKINS_AGENT_WORKDIR=/home/jenkins/agent jenkins/inbound-agent:latest-jdk21

What you see. The first time, Docker does not have the image yet: Unable to find image … locally, then Pulling from jenkins/inbound-agent and several Downloading / Download complete lines (about 300 MB, 1 to 3 minutes; lines marked Already exists are shared with your other images). It ends with Status: Downloaded newer image… and a long ID of 64 letters and digits, then the prompt comes back.

The long ID means the container started in the background (-d). That is why you do not see INFO: Connected here: the agent writes it in its logs (step C).

💡 Save time in class: download the image at the start of the session (or at home) with docker pull jenkins/inbound-agent:latest-jdk21. When 30 students download 300 MB at the same moment, the Wi-Fi is slow.

What each part does:

  • -d --name linux-agent: run in the background, with a name you can reuse (docker logs, docker stop).
  • --init: a tiny process manager in the container, so that build processes are cleaned up correctly.
  • -e JENKINS_URL=http://host.docker.internal:8080: where Jenkins is. Inside a container, localhost is the container itself; host.docker.internal is your PC, where port 8080 leads to Jenkins (Jenkins on Windows, or the Jenkins container through its -p 8080:8080).
  • JENKINS_SECRET, JENKINS_AGENT_NAME: who it is. The name must be exactly the node name.
  • JENKINS_WEB_SOCKET=true: connect through the web port, no port 50000 needed.
  • jenkins/inbound-agent:latest-jdk21: the official agent image, with Java 21 and git.

C. Check

  1. docker logs linux-agent: the last line must be INFO: Connected. Not there yet? Wait 5 seconds and run it again, or follow the logs live with docker logs -f linux-agent (Ctrl + C stops following; the agent keeps running).
  2. Refresh Manage Jenkins › Nodes: linux-agent has no red cross, and its Architecture is Linux (amd64).
"error during connect" or "cannot find the file specified … dockerDesktopLinuxEngine"

Docker Desktop is not running. Start it, wait for Engine running, then run the docker run line again.

I ran the command with PASTE_THE_SECRET_HERE (or a wrong secret)

The logs show 403, Forbidden or Unauthorized, and the container stops. Remove it, then run the line again with your secret (no new download this time):

docker rm -f linux-agent
docker logs says "Failed to connect to http://host.docker.internal:8080/" or "Connection refused"

The agent cannot reach Jenkins. Check that Jenkins runs and opens in your browser on http://localhost:8080. If your Jenkins uses another port, recreate the container with that port: docker rm -f linux-agent, then the docker run line with the right port in JENKINS_URL.

docker logs says "403", "Unauthorized" or "is not a valid agent name"

The secret or the name is wrong. Copy the secret again from the node page (no space at the start or end), check that JENKINS_AGENT_NAME is exactly linux-agent, then docker rm -f linux-agent and run the line again.

⚠️ Run the long docker run line only once. It creates the container, with its settings and the secret. After that, use only docker stop linux-agent and docker start linux-agent (after a reboot, after closing Docker Desktop): no secret to type again.
If you run the long line again, Docker says The container name "/linux-agent" is already in use. Use docker start linux-agent instead. Run docker rm -f linux-agent and the long line again only if the secret changed (node recreated) or to change a setting.

D. Same job, two machines

Online is not enough: check that the agent builds, and compare it with the controller. Create a Pipeline job named hello-agent with this script. The first stage asks for the controller (its label is built-in), the second for the agent.

hello-agent
pipeline {
    agent none                          // each stage chooses its node
    stages {
        stage('On the controller') {
            agent { label 'built-in' }      // the built-in node has this label
            steps {
                echo "I am ${env.NODE_NAME}, workspace ${env.WORKSPACE}"
                script {
                    if (isUnix()) { sh 'uname -a' } else { bat 'ver' }
                }
            }
        }
        stage('On the Linux agent') {
            agent { label 'linux' }
            steps {
                echo "I am ${env.NODE_NAME}, workspace ${env.WORKSPACE}"
                sh 'uname -a'
            }
        }
    }
}
🔮 Predict first. Write your answer down before you run, then compare.
  1. Where will each stage say it runs? Which system will each one print: Windows or Linux? (It depends on where your Jenkins runs.)

Build Now, then Console Output. Find the two Running on lines and compare the two stages.

Show the explanation

Same script, two machines, two workspaces. Until today every build ran in the first column, inside the controller, next to its secrets. From now on, builds go to the second column. isUnix() lets one stage work on both kinds of controller: sh on Linux, bat on Windows.

A stage stays in the queue? Hover over it on the home page: the label must be exactly linux (or built-in), and the node must be online.

🔮 Predict first. Write your answer down before you run, then compare.
  1. You run docker stop linux-agent, then docker start linux-agent. Will the agent come back online by itself? Do you need a new secret?

Try it, and refresh the Nodes page after each command.

✅ Checkpoint 2: answer in report.txt, in your own words (one or two lines each).
  1. Tomorrow you restart your PC and linux-agent is offline. Which single command brings it back, and why don't you need a new secret?
  2. Who starts the connection: does Jenkins call the agent, or does the agent call Jenkins? Why is that direction convenient for a laptop on the school Wi-Fi?
See the answer
  1. docker start linux-agent. The container keeps its settings (the -e variables), including the secret. The secret belongs to the node created in Jenkins: it only changes if you delete and create the node again.
  2. The agent calls Jenkins (inbound agent, the method “Launch agent by connecting it to the controller”). Jenkins never needs to reach the laptop: the laptop can be behind the Wi-Fi router or a firewall, with no open port. With WebSocket, it even uses the same address as your browser (port 8080).
