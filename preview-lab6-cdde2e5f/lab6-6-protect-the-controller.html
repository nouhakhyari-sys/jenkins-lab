Lab 6 · Distributed Builds with Agents

6. Protect the Controller

🎯 Why this step? A build runs code from Git. On the controller, that code can read the Jenkins home folder: secrets/, credentials.xml (your Docker Hub token from Lab 5), the configuration of every job. The Jenkins documentation recommends 0 executors on the built-in node: the controller only plans, agents build. Then you test what happens when an agent disappears.

A. No more builds on the controller

  1. Manage Jenkins › Nodes › Built-In Node › Configure: Number of executors = 0. Save.
🔮 Predict first. Write your answer down before you run, then compare.
  1. You run where-am-i again (with agent any in the Anywhere stage, as in the original script). What happens to each stage?
  1. Put agent any back in the Anywhere stage if you changed it, and run where-am-i. Watch the stage view and the Build Queue, and hover over the waiting item.
  2. Find two different ways to make it finish, apply one, and run again.
Show the explanation

The first two stages run normally. Anywhere waits forever: the controller has no executor, and both agents refuse a job with no label. Two fixes:

  • in the Jenkinsfile, ask for a label: agent { label 'linux || windows' };
  • or on linux-agent, Configure › Usage › Use this node as much as possible: it then accepts agent any too.

This is a real situation: when a company sets the controller to 0 executors, every old job with agent any must find an agent that accepts it.

B. When an agent goes offline

  1. Stop the Linux agent: docker stop linux-agent. Refresh the Nodes page.
  2. Run build-once. Watch the Build Queue and the Console Output for one minute.
  3. Start the agent again: docker start linux-agent. Watch the build.
Show the explanation

The build waits: “linux-agent is offline” / “Waiting for next available executor on ‘linux’”. Nothing is lost. As soon as the agent reconnects, the build continues by itself. A build fails only if the agent disappears during a step (try it in challenge 3 of part 8, with a timeout).

C. When an agent stops during a step

B showed an agent that was off before the build. Now it disappears in the middle of a step. Create a Pipeline job named long-job (2 minutes of work on the Linux agent):

long-job
pipeline {
    agent { label 'linux' }
    stages {
        stage('Long step') {
            steps {
                sh 'for i in $(seq 1 60); do echo "step $i of 60"; sleep 2; done'
            }
        }
    }
}
🔮 Predict first. Write your answer down before you run, then compare.
  1. Case B: the build waited and continued. Will this one also wait and continue where it stopped?
  1. Build Now and open the Console Output. When you see step 5 of 60, run docker stop linux-agent.
  2. Watch the console: what does Jenkins write?
  3. Run docker start linux-agent and watch the end of the build (it can take a minute).
Show the explanation

The console says that Jenkins cannot contact linux-agent. docker stop killed the loop that was running in the container: the work done so far is lost. When the agent comes back, Jenkins finds that the command is not running any more, and the build ends red (FAILURE, often script returned exit code -1). It does not restart the step by itself.

The agent stops…Result
before the build gets it (B)the build waits, then runs when the agent is back
during a step (C)the build fails: the step must be run again

That is why a timeout (challenge 3 of part 8) and a second agent with the same label (part 7) matter in production.

✅ Checkpoint 6: answer in report.txt, in your own words (one or two lines each).
  1. With 0 executors on the controller, one stage waited forever. Explain why, and give two different fixes.
  2. You stopped linux-agent before a build. Did the build fail or wait? What did it do when the agent came back?
  3. In C you stopped the agent during a step. What was the result, and why is it different from B?
See the answer
  1. The controller has 0 executors and both agents only accept jobs with a matching label. agent any has no label: no node accepts it, so it waits. Fix 1: give the stage a label, for example agent { label 'linux || windows' }. Fix 2: on one agent, set Usage to Use this node as much as possible.
  2. It waited in the queue (“linux-agent is offline” / “Waiting for next available executor”). Nothing failed. When the agent came back, the build started by itself. A build only fails if the agent disappears during the build.
  3. The build failed. The command was running on the agent; docker stop killed it, so its work was lost and Jenkins cannot continue it. Before the build (B), nothing had started yet, so waiting was enough. A step that is interrupted must be run again.
