Lab 6 · Distributed Builds with Agents

4. Send Stages to Agents with Labels

🎯 Why this step? A stage does not ask for a machine by name: it asks for a label, what the machine must be able to do. Jenkins picks a free node that matches. With agent none at the top, each stage chooses its own node.

Create a Pipeline job named where-am-i with this script. Read it first.

where-am-i
pipeline {
    agent none
    stages {
        stage('On Linux') {
            agent { label 'linux' }
            steps {
                sh 'echo "I am $NODE_NAME, my workspace is $WORKSPACE"'
                sh 'uname -a'
                sh 'java -version'
            }
        }
        stage('On Windows') {
            agent { label 'windows' }
            steps {
                bat 'echo I am %NODE_NAME%, my workspace is %WORKSPACE%'
                bat 'ver'
                bat 'java -version'
            }
        }
        stage('Anywhere') {
            agent any
            steps {
                echo "This stage ran on ${env.NODE_NAME}"
            }
        }
    }
}
🔮 Predict first. Write your answer down before you run, then compare.
  1. Which node runs each of the three stages? Careful with the third one: what does agent any mean when both agents only accept jobs “with label expressions matching this node”?
  2. Jenkins on Windows: you will run sh steps today. On which machine?

Run and observe

  1. Build Now, then Console Output. Find each Running on … line: it names the node and the workspace folder.
  2. Compare the outputs of uname -a and ver, and of the two java -version: two machines, two systems.
  3. Look at Manage Jenkins › Nodes › linux-agent › Build History: the build is listed on the agent too.
Show the explanation
  • On Linux ran on linux-agent, in /home/jenkins/agent/workspace/where-am-i; On Windows on windows-agent, in C:\jenkins-agent\workspace\where-am-i.
  • Anywhere ran on the built-in node (“Jenkins”): agent any has no label, and both agents refuse jobs without a matching label. Only the controller accepts it. Remember this for part 6.
  • The agent decides between sh and bat: sh works on linux-agent even if your Jenkins runs on Windows.
💥 Break it on purpose (2 min). In the On Windows stage, write label 'Windows' (capital W) and run. The build does not fail: it waits. On the home page, hover over the waiting build in the Build Queue and read the reason. Cancel it (the ✕ next to it) and put the lower-case w back.
What did Jenkins say?

There are no nodes with the label ‘Windows’. Labels are case-sensitive. A wrong label never turns the build red: it stays in the queue, forever. When a build “does nothing”, look at the queue first.

Label expressions

A label can be combined: linux && java (both), linux || windows (one of them), java && !windows (java, but not windows). Replace the label of the Anywhere stage by agent { label 'java && !windows' }, predict the node, and run.

Where did it run?

On linux-agent: it is the only node with java and without windows. The controller has no label java, so it is not chosen.

✅ Checkpoint 4: answer in report.txt, in your own words (one or two lines each).
  1. Before running, where did you think the Anywhere stage would run? Where did it run, and which setting of your two agents explains it?
  2. Your company adds a third node with the labels linux gpu. Write the label expression of a stage that needs Linux but must never use this expensive GPU machine.
See the answer
  1. On the built-in node (the controller, “Jenkins”). Both agents are set to Only build jobs with label expressions matching this node: agent any has no label, so they refuse it. The only node that accepts any job is the controller.
  2. linux && !gpu. (linux alone could pick the GPU machine.)
