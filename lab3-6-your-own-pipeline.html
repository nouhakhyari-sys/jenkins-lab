Lab 3 · Build a Java Project

6. Your Own Java Pipeline

Now write the pipeline yourself, in Jenkins, so you can change it. The code still comes from GitHub, but this time your script downloads it with the git step in a Checkout stage. Try each exercise first; open the solution only to check.

Exercise A: the pipeline in a Script box (10 min)

  1. New Item › my-java-pipeline › Pipeline › OK. In the Pipeline section, keep Definition: Pipeline script.
  2. Start from the Jenkinsfile you read in part 2: open lab2/java-app on GitHub, copy Jenkinsfile (Docker) or Jenkinsfile-windows (Windows) and paste it into the Script box.
  3. In part 3, Jenkins downloaded the repository by itself because the script came from Git. In a Script box it does not: add a first stage Checkout that runs the git step on https://github.com/nouhakhyari-sys/jenkins-labs-template.git, branch main.
  4. Save, Build Now. Check: the build is green and the stages are Checkout, Build, Test, Package.
Hint: Pipeline Syntax › Snippet Generator, Sample Step git: Git. Repository URL: the address above, Branch: main, Credentials: - none -. Click Generate Pipeline Script and put the line inside stage('Checkout') { steps { … } }, as the first stage.
Built before adding Checkout? The Build stage fails with error: file not found: src/Calculator.java (or src\Calculator.java on Windows). The workspace is empty: nothing was downloaded from GitHub. Add the Checkout stage and build again.
Show the solution: Jenkins in Docker
pipeline {
    agent any

    options {
        timestamps()
    }

    parameters {
        booleanParam(name: 'SIMULATE_BUG', defaultValue: false,
                     description: 'Tick to put a bug in the calculator')
    }

    stages {
        stage('Checkout') {
            steps {
                git branch: 'main', url: 'https://github.com/nouhakhyari-sys/jenkins-labs-template.git'
            }
        }
        stage('Build') {
            steps {
                dir('lab2/java-app') {
                    sh 'javac -d build/classes src/Calculator.java test/CalculatorTest.java'
                }
            }
        }
        stage('Test') {
            steps {
                dir('lab2/java-app') {
                    sh "java -DsimulateBug=${params.SIMULATE_BUG} -cp build/classes CalculatorTest"
                }
            }
            post {
                always {
                    junit 'lab2/java-app/build/test-results/*.xml'
                }
            }
        }
        stage('Package') {
            steps {
                dir('lab2/java-app') {
                    sh 'jar cfe build/calculator.jar Calculator -C build/classes .'
                }
                archiveArtifacts artifacts: 'lab2/java-app/build/calculator.jar', fingerprint: true
            }
        }
    }

    post {
        always {
            cleanWs()
        }
    }
}

Your script may have a few more lines (for example javac -version or java -jar): that is fine.

Exercise B: a manual approval before deploying (10 min)

In the course, continuous delivery means every build is ready to deploy, but a person decides. The input step does exactly that: the pipeline stops and waits for a click.

  1. Click Configure. After the Package stage, add a stage Deploy with two steps:
    • an input that asks Deploy calculator.jar to production?, with a button named Deploy;
    • an echo that prints Deploying calculator.jar to production...
  2. Save, then Build with Parameters › Build.
  3. The build stops at Deploy (paused). Hover the Deploy cell in Stage View, or open Console Output: click Deploy to continue, or Abort to stop.
  4. Run it twice: once with Deploy (green build), once with Abort (grey build, ABORTED).
Hint: Snippet Generator, Sample Step input: Wait for interactive input: Message = the question, Advanced › OK Button Caption = Deploy. For the second line, Sample Step echo: Print Message. For the stage itself, Declarative Directive Generator › stage: Stage, name Deploy, directive steps. The new stage goes after the closing } of Package and before the } that closes stages.
Show the solution: the Deploy stage (Docker and Windows)
        stage('Deploy') {
            steps {
                input message: 'Deploy calculator.jar to production?', ok: 'Deploy'
                echo 'Deploying calculator.jar to production...'
                echo 'Done: version ' + env.BUILD_NUMBER + ' is live!'
            }
        }
Remove the approval and you get continuous deployment: every green build goes to production automatically. Which one would you choose for a bank? For a blog?

Exercise C (if you have time): choose where to deploy

  1. Add a second parameter, TARGET: a drop-down list with the two choices test and production.
  2. Change the Deploy stage so that the question and the message use the chosen value instead of the word production.
  3. Save, then Build with Parameters: choose TARGET = production, click Build, approve. The message says "production". Try again with test.
Hint: Declarative Directive Generator, parameters › Choice Parameter (one choice per line). In the steps, read the value with ${params.TARGET}, inside double quotes.
Show the solution: TARGET parameter and Deploy stage

1. Add this line inside parameters { }, under SIMULATE_BUG:

        choice(name: 'TARGET', choices: ['test', 'production'],
               description: 'Where to deploy')

2. Replace your Deploy stage of exercise B by this one (same in Docker and Windows):

        stage('Deploy') {
            steps {
                input message: "Deploy calculator.jar to ${params.TARGET}?",
                      ok: 'Deploy'
                echo "Deploying calculator.jar to ${params.TARGET}..."
            }
        }

Both pieces are needed: the first creates the drop-down list, the second uses the chosen value.
