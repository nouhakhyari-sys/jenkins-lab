Lab 3 · Build a Java Project

6. Your Own Java Pipeline

Now write the pipeline yourself, in Jenkins, so you can change it. The code still comes from GitHub, but this time with the git step in a Checkout stage.

Exercise A: the pipeline in a Script box (10 min)

  1. New Item › my-java-pipeline › Pipeline › OK.
  2. In the Pipeline section, keep Definition: Pipeline script.
  3. Paste the version that matches your Jenkins, then Save and Build Now.
my-java-pipeline: Jenkins in Docker
pipeline {
    agent any

    options {
        timestamps()
    }

    parameters {
        booleanParam(name: 'SIMULATE_BUG', defaultValue: false,
                     description: 'Tick to put a bug in the calculator')
    }

    stages {
        stage('Checkout') {
            steps {
                git branch: 'main', url: 'https://github.com/nouhakhyari-sys/jenkins-labs-template.git'
            }
        }
        stage('Build') {
            steps {
                dir('lab2/java-app') {
                    sh 'javac -d build/classes src/Calculator.java test/CalculatorTest.java'
                }
            }
        }
        stage('Test') {
            steps {
                dir('lab2/java-app') {
                    sh "java -DsimulateBug=${params.SIMULATE_BUG} -cp build/classes CalculatorTest"
                }
            }
            post {
                always {
                    junit 'lab2/java-app/build/test-results/*.xml'
                }
            }
        }
        stage('Package') {
            steps {
                dir('lab2/java-app') {
                    sh 'jar cfe build/calculator.jar Calculator -C build/classes .'
                }
                archiveArtifacts artifacts: 'lab2/java-app/build/calculator.jar', fingerprint: true
            }
        }
    }

    post {
        always {
            cleanWs()
        }
    }
}

Optional: write the git line with the Snippet Generator

Click Pipeline Syntax. In Sample Step choose git: Git. Repository URL: the address above, Branch: main, Credentials: - none -. Click Generate Pipeline Script: you get the same git line as in the script.

Check: the build is green and the stages are Checkout, Build, Test, Package.

Exercise B: a manual approval before deploying (10 min)

In the course, continuous delivery means every build is ready to deploy, but a person decides. The input step does exactly that: the pipeline stops and waits for a click.

  1. Click Configure. After the Package stage (after its closing }, before the } that closes stages), add this stage:
Add after the Package stage (same in Docker and Windows)
        stage('Deploy') {
            steps {
                input message: 'Deploy calculator.jar to production?', ok: 'Deploy'
                echo 'Deploying calculator.jar to production...'
                echo 'Done: version ' + env.BUILD_NUMBER + ' is live!'
            }
        }
  1. Save, then Build with Parameters › Build.
  2. The build stops at Deploy (blue, paused). Hover the Deploy cell in Stage View, or open Console Output: click Deploy to continue, or Abort to stop.
  3. Run it twice: once with Deploy (green build), once with Abort (grey build, ABORTED).
Remove the approval and you get continuous deployment: every green build goes to production automatically. Which one would you choose for a bank? For a blog?

Exercise C (if you have time): choose where to deploy

  1. In parameters, add a second parameter under SIMULATE_BUG:
Add inside parameters { }
        choice(name: 'TARGET', choices: ['test', 'production'],
               description: 'Where to deploy')
  1. Replace your Deploy stage with this one:
Deploy stage that uses the parameter
        stage('Deploy') {
            steps {
                input message: "Deploy calculator.jar to ${params.TARGET}?", ok: 'Deploy'
                echo "Deploying calculator.jar to ${params.TARGET}..."
            }
        }
  1. Save, then Build with Parameters: choose TARGET = production, click Build, approve. The message says "production".
