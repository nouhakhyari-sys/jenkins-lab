Lab 6 · Distributed Builds with Agents

7. An Agent that Runs Docker

🎯 Why this step? Your final project builds a Docker image, pushes it and starts staging and production containers. In Lab 5 the controller ran these docker commands. Now builds go to agents, but jenkins/inbound-agent has no docker command. You build your own agent image, with Docker inside: feature 13 of the project.

A. Build the agent image

  1. Create a folder docker-agent (for example in your jenkins-labs repository, under lab6) and, in it, a file named Dockerfile (no extension) with:
docker-agent/Dockerfile
FROM jenkins/inbound-agent:latest-jdk21
USER root
COPY --from=docker:27-cli /usr/local/bin/docker /usr/local/bin/docker
RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*
  • FROM jenkins/inbound-agent:latest-jdk21: start from the official agent (Java 21, agent.jar).
  • COPY --from=docker:27-cli …: copy only the docker command (the client) from the official Docker image. No Docker engine inside: the agent will use the engine of your PC.
  • curl: for the smoke tests of your project.
  1. In PowerShell, in the folder docker-agent: docker build -t docker-agent . (the dot is the folder).

B. Create the node and start it

  1. Manage Jenkins › Nodes › New Node: docker-agent, Permanent Agent (or Copy Existing Node from linux-agent). Number of executors 1, Remote root directory /home/jenkins/agent, Labels linux docker, Usage Only build jobs with label expressions matching this node, Launch by connecting it to the controller (Use WebSocket: optional, as for linux-agent). Save, and copy the secret.
  2. Start it (one line, with the secret of docker-agent):
Start docker-agent (one line)
docker run -d --name docker-agent --init --user root -v /var/run/docker.sock:/var/run/docker.sock --add-host=host.docker.internal:host-gateway -e JENKINS_URL=http://host.docker.internal:8080 -e JENKINS_SECRET=PASTE_THE_SECRET_OF_DOCKER_AGENT -e JENKINS_AGENT_NAME=docker-agent -e JENKINS_WEB_SOCKET=true -e JENKINS_AGENT_WORKDIR=/home/jenkins/agent docker-agent

The new parts, compared with linux-agent:

  • -v /var/run/docker.sock:/var/run/docker.sock: shares the socket of Docker Desktop. The docker command in the agent talks to the Docker engine of your PC.
  • --user root: the socket only accepts root.
  • docker-agent at the end: your image, not jenkins/inbound-agent.

As in part 2, the command prints a long ID (the container runs in the background). Check: docker logs docker-agent ends with INFO: Connected, and the Nodes page shows docker-agent online. Wrong secret? docker rm -f docker-agent and run the line again.

🔒 Only on your own PC. The Docker socket gives full control of Docker, and through it of the machine. A build on this agent could start any container, as root. Never do this on a shared server: companies use rootless builders such as kaniko (Session 9) or one fresh VM per build.

C. Build an image on the agent

Create a Pipeline job named image-on-agent. The jar is built on a linux node, then carried to the docker node, which builds and runs an image: the same shape as your project.

image-on-agent
pipeline {
    agent none
    stages {
        stage('Build') {
            agent { label 'linux' }
            steps {
                writeFile file: 'src/Hello.java', text: '''
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello from " + System.getProperty("os.name")
            + ", Java " + System.getProperty("java.version"));
    }
}
'''
                sh 'javac --release 17 -d classes src/Hello.java'
                sh 'jar cfe hello.jar Hello -C classes .'
                stash name: 'app', includes: 'hello.jar'
            }
        }
        stage('Docker image') {
            agent { label 'docker' }
            steps {
                unstash 'app'
                writeFile file: 'Dockerfile', text: '''
FROM eclipse-temurin:21-jre
COPY hello.jar /app/hello.jar
CMD ["java", "-jar", "/app/hello.jar"]
'''
                sh 'docker build -t hello-agent:${BUILD_NUMBER} .'
                sh 'docker run --rm hello-agent:${BUILD_NUMBER}'
            }
            post { always { cleanWs() } }
        }
    }
}
🔮 Predict first. Write your answer down before you run, then compare.
  1. Which node can run the Build stage? (Look at the labels of your three nodes: more than one may match.)
  2. After the build, will docker images on your PC show hello-agent?
  1. Build Now. In the Console Output, find the two Running on lines and the line Hello from Linux, Java 21… printed by the container.
  2. In PowerShell: docker images hello-agent. Take the screenshot docker-agent.png: the console with Running on docker-agent and the Hello line.
Show the explanation
  • Build asks for linux: linux-agent and docker-agent both have this label, so either can take it. That is normal: agents with the same label are interchangeable (fungible).
  • Docker image asks for docker: only docker-agent. unstash brings the jar, docker build sends the workspace to the engine of your PC, which builds the image.
  • Yes: the image is on your PC, because the engine of your PC built it. In your project, the staging container started by this agent is also on your PC, so http://host.docker.internal:8081 works as in Lab 5.
"docker: not found" in the Docker image stage

The stage ran on a node without Docker: check that its label is docker, and that the container was started from your image docker-agent, not jenkins/inbound-agent (docker ps, IMAGE column).

"permission denied while trying to connect to the Docker daemon socket"

--user root is missing. docker rm -f docker-agent, then start it again with the full command.

"Cannot connect to the Docker daemon at unix:///var/run/docker.sock"

The -v /var/run/docker.sock:/var/run/docker.sock part is missing, or Docker Desktop is stopped. Check Engine running, then recreate the container.

D. One agent down, the other takes over

You now have two nodes with the label linux: linux-agent (linux java) and docker-agent (linux docker).

  1. Stop the first one: docker stop linux-agent.
  2. Create a Pipeline job named failover with the script below and run it. Read the Running on line.
  3. Start it again: docker start linux-agent.
failover
pipeline {
    agent { label 'linux' }
    stages {
        stage('Who builds?') {
            steps {
                echo "I am ${env.NODE_NAME}"
            }
        }
    }
}
🔮 Predict first. Write your answer down before you run, then compare.
  1. linux-agent is stopped. Will the build wait, as in part 6B?
Show the explanation

It does not wait: it runs on docker-agent (I am docker-agent). The job asks for the label linux, not for a machine name, and another node with that label was free. This is failover: with two interchangeable (fungible) agents, losing one does not stop the team. In part 6B there was only one node with the label, so the build had to wait.

That is the rule for your project: in the Jenkinsfile, ask for labels (linux, docker), never for linux-agent.

✅ Checkpoint 7: answer in report.txt, in your own words (one or two lines each).
  1. The image jenkins/inbound-agent has no docker command. What did you add, and what does the -v /var/run/docker.sock part of the command give to the agent?
  2. After a build of image-on-agent, you type docker images in PowerShell on your PC and you see hello-agent. Why is the image on your PC, although it was built "inside" the agent container?
  3. Why must you never start an agent with --user root and docker.sock on a shared company server?
  4. With linux-agent stopped, the job failover did not wait. Where did it run, and why? What would have happened with agent { label 'linux-agent' }?
See the answer
  1. The docker command (the client), copied from the official image docker:27-cli. The -v part shares the socket of Docker Desktop with the container: the docker command inside the agent talks to the Docker engine of your PC.
  2. The agent has only the docker client. The image is built by the Docker engine of your PC, through the socket. So the image, and the containers the agent starts, live on your PC, next to Jenkins: that is why staging on port 8081 works from an agent.
  3. Whoever controls the Docker engine controls the machine: a build could start a container that mounts the whole disk, as root. On a shared server, any developer who can push a Jenkinsfile would become administrator. Companies use rootless tools (kaniko, Session 9) or one VM per build instead.
  4. On docker-agent: it also has the label linux and was free, so Jenkins chose it (failover). With label 'linux-agent' (the name of one machine), only that machine matches: the build would have waited until linux-agent came back.
