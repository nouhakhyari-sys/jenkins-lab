Lab 4 · Freestyle Projects and Blue Ocean

2. Freestyle vs Pipeline

A Freestyle job is one block of work. To build a workflow with several steps (build, then deploy), you must chain several jobs. Try it.

Exercise A: Chain two jobs

  1. Create a new Freestyle project called freestyle-deploy.
  2. Keep it minimal: no parameter, no Git, no post-build action. Add only one build step (Execute shell or Execute Windows batch command) with: echo Deploying calculator.jar... Save.
  3. Open freestyle-calculator › Configure. In Post-build Actions, add Build other projects. Projects to build: freestyle-deploy. Keep the option Trigger only if build is stable. Save.
  4. Run freestyle-calculator without the bug: when it ends green, freestyle-deploy starts by itself.
  5. Run it again with SIMULATE_BUG ticked: the build is yellow, and freestyle-deploy does not start.
  6. On the page of freestyle-calculator, find Downstream Projects; on freestyle-deploy, find Upstream Projects.
See the problem? Your "pipeline" is now spread over two jobs, each configured on its own page. A third job would need a third page. And freestyle-deploy has its own workspace: it cannot even see calculator.jar. In a pipeline, the same flow is one file, with stages that share one workspace.

Exercise B: Where does Jenkins keep a Freestyle job?

Every form you filled in is saved by Jenkins in a file called config.xml, inside the jobs folder of the Jenkins home. Open it:

  • Docker: docker exec jenkins-local cat /var/jenkins_home/jobs/freestyle-calculator/config.xml
  • Windows: open jobs\freestyle-calculator\config.xml in your Jenkins home folder with Notepad (for example C:\Users\<you>\.jenkins, or the folder in your JENKINS_HOME).

Create a text file config.txt, copy the template below, and fill in each line with what you find in the XML. The tag to look for is given on each line. This file is part of your hand-in (lab4/config.txt).

config.txt: fill in each line
Job: freestyle-calculator

1. Build commands                     <command>                  :
2. Parameter name and default value   <name>, <defaultValue>     :
3. Git repository URL and branch      <url>, branch <name>       :
4. Test report path                   <testResults>              :
5. Archived file, fingerprint?        <artifacts>, <fingerprint> :
6. Downstream job and its condition   <childProjects>, <threshold>:

Job: java-calculator (Lab 3)
7. Are the build commands in this file? (yes / no)                       :
8. What do you find instead?           <url>, <scriptPath>        :

Every job has a config.xml, pipelines too. For questions 7 and 8, open the config.xml of your Lab 3 job java-calculator the same way, and compare. It must be a job whose Definition is Pipeline script from SCM (it reads the Jenkinsfile from GitHub): in its XML you see CpsScmFlowDefinition. If you see CpsFlowDefinition and a <script> tag instead, you opened a pipeline typed in the Script box: take another job.

What you just saw: Jenkins stores every job in a config.xml. The difference is what is inside. In a Freestyle job, it contains the whole recipe (the commands), and this file lives only inside Jenkins: not in Git, not reviewed, lost if the Jenkins server is lost. In a pipeline from SCM, it only contains where to find the Jenkinsfile; the recipe itself is in Git. (A pipeline typed in the Script box is stored in config.xml too, in a <script> tag: that is why Jenkinsfiles belong in Git.)

Questions

1. A teammate changed the build command of a Freestyle job last week, and the build is broken. How do you find what changed?

It is hard: the change is in config.xml inside Jenkins, with no history by default (only with an extra plugin such as Job Configuration History). With a Jenkinsfile, git log and git diff show who changed which line, and when, and the change could have been reviewed in a pull request.

2. Why did freestyle-deploy not start when SIMULATE_BUG was ticked?

The option Trigger only if build is stable: a yellow (UNSTABLE) build is not stable. It is the same idea as Continuous Delivery: a build with a failed test must not go to deployment.

3. When would you still choose a Freestyle job today?

For a small, simple task with one step and no review needed: for example a nightly script that cleans a folder, or a quick test of a command. For anything that builds, tests and deploys an application, use a pipeline. You will answer this question again in your hand-in.
