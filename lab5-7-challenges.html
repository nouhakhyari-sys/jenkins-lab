7. Challenges

Finished early? Three challenges, independent of each other, each bringing one more idea of the course into your pipeline. Do them in any order. For each one you do, write in report.txt the problem it solves (the 🤔 question of the challenge).

Challenge 1: Push the image to a registry (Docker Hub)

Until now the image only exists on your computer. In a real team it goes to a registry, where staging and production servers download it. Pushing needs a login: the password must never be written in the Jenkinsfile, which is in Git.

  1. Create a free account on hub.docker.com. Then Account settings › Personal access tokens › Generate new token, access Read & Write. Copy the token.
  2. In Jenkins: Manage Jenkins › Credentials › System › Global credentials › Add Credentials. Kind Username with password, Username: your Docker Hub username, Password: the token, ID: dockerhub.
  3. Add this stage after Docker image:
Push stage (Jenkins in Docker)
        stage('Push') {
            when {
                expression { currentBuild.currentResult == 'SUCCESS' }
            }
            steps {
                withCredentials([usernamePassword(credentialsId: 'dockerhub',
                        usernameVariable: 'DH_USER', passwordVariable: 'DH_TOKEN')]) {
                    sh 'echo $DH_TOKEN | docker login -u $DH_USER --password-stdin'
                    sh 'docker tag $IMAGE:$VERSION $DH_USER/$IMAGE:$VERSION'
                    sh 'docker push $DH_USER/$IMAGE:$VERSION'
                }
            }
        }
Push stage (Jenkins on Windows)
        stage('Push') {
            when {
                expression { currentBuild.currentResult == 'SUCCESS' }
            }
            steps {
                withCredentials([usernamePassword(credentialsId: 'dockerhub',
                        usernameVariable: 'DH_USER', passwordVariable: 'DH_TOKEN')]) {
                    bat 'echo %DH_TOKEN%| docker login -u %DH_USER% --password-stdin'
                    bat 'docker tag %IMAGE%:%VERSION% %DH_USER%/%IMAGE%:%VERSION%'
                    bat 'docker push %DH_USER%/%IMAGE%:%VERSION%'
                }
            }
        }
  • withCredentials gives the username and token to the steps inside it only, as environment variables.
  • The commands use single quotes: the shell reads the secret, Groovy never puts it in the script text. In the Console Output, the token is shown as ****.
  • docker tag gives the image a second name, <your-user>/calc-web:1.0.N: on Docker Hub an image belongs to an account.

Check that the image reached Docker Hub:

  1. In the Console Output of the build, the Push stage ends with lines Pushed (or Layer already exists) and a digest: sha256:… line.
  2. Open hub.docker.com and log in. Click My Hub › Repositories: you see <your-user>/calc-web, with Last Pushed a few minutes ago. This list shows repositories, not versions.
  3. Click <your-user>/calc-web, then the Tags tab: here are the versions, one tag per pushed build (1.0.17, 1.0.18…), with the push date and size.
  4. Push another build and refresh the Tags tab: a new tag appears.

The Visibility column says Public: anyone can now run your app on their own computer, without Jenkins and without the code: docker run -d -p 8090:8080 <your-user>/calc-web:1.0.N, then http://localhost:8090/add/2/3. Try it with the image of a classmate! (To make it private: the repository › Settings › Visibility settings.)

📸 For challenge.png: the Tags tab of your repository.

🤔 Think: why is the token stored in Jenkins Credentials and not in the Jenkinsfile? Why do staging and production servers need a registry?

Challenge 2: Block vulnerable images (Trivy)

Scan the image for known vulnerabilities (CVE) after it is built and before it is pushed or deployed. Trivy runs as a container, so there is nothing to install. Add this stage after Docker image, before Push and the deployments:

Security scan stage (Jenkins in Docker)
        stage('Security scan') {
            when {
                expression { currentBuild.currentResult == 'SUCCESS' }
            }
            steps {
                sh "docker run --rm -v /var/run/docker.sock:/var/run/docker.sock -v trivy-cache:/root/.cache/ aquasec/trivy:0.73.0 image --no-progress --scanners vuln --timeout 15m --exit-code 1 --severity CRITICAL ${IMAGE}:${VERSION}"
            }
        }
Security scan stage (Jenkins on Windows)
        stage('Security scan') {
            when {
                expression { currentBuild.currentResult == 'SUCCESS' }
            }
            steps {
                bat "docker run --rm -v /var/run/docker.sock:/var/run/docker.sock -v trivy-cache:/root/.cache/ aquasec/trivy:0.73.0 image --no-progress --scanners vuln --timeout 15m --exit-code 1 --severity CRITICAL ${IMAGE}:${VERSION}"
            }
        }
  • The bind mount of docker.sock lets Trivy see the images of your Docker engine.
  • -v trivy-cache:/root/.cache/: a volume for Trivy's vulnerability databases (several hundred MB). Without it, --rm deletes them with the container and every scan downloads them again (about 5 minutes). With it, only the first scan is slow; the next ones take seconds.
  • --timeout 15m: the first scan downloads about 1 GB of databases and can exceed Trivy's default limit of 5 minutes (context deadline exceeded). --scanners vuln: look only for known vulnerabilities, not for passwords in files (faster).
  • --severity CRITICAL --exit-code 1: if a CRITICAL vulnerability is found, the command fails, the stage is red, and the image is never deployed. The first run downloads Trivy's vulnerability database: it takes a minute.

🤔 Think: why is the scan placed after Docker image but before Push and the deployments? What would go wrong if it ran after deployment?

Pin your tools too. The scanner uses a precise tag (aquasec/trivy:0.73.0), not latest. In March 2026, some Trivy releases were themselves compromised in a supply-chain attack (CVE-2026-33634): a team that pulled latest at that moment ran a malicious scanner. A security tool is a dependency like any other.

Challenge 3: Roll back production in one minute

Version 1.0.15 is in production and customers report a bug. With versioned images, going back to 1.0.14 needs no rebuild: the old image still exists. Create a new pipeline job calc-web-rollback:

calc-web-rollback (Jenkins in Docker)
pipeline {
    agent any

    parameters {
        string(name: 'ROLLBACK_TO', defaultValue: '',
               description: 'A version already built, for example 1.0.12')
    }

    stages {
        stage('Check the image') {
            steps {
                sh "docker image inspect calc-web:${params.ROLLBACK_TO} > /dev/null"
            }
        }
        stage('Rollback production') {
            steps {
                input message: "Put calc-web:${params.ROLLBACK_TO} back in production?", ok: 'Rollback'
                sh 'docker rm -f calc-prod || true'
                sh "docker run -d --name calc-prod -p 8082:8080 calc-web:${params.ROLLBACK_TO}"
                echo "Production is back to version ${params.ROLLBACK_TO}"
            }
        }
    }
}
calc-web-rollback (Jenkins on Windows)
pipeline {
    agent any

    parameters {
        string(name: 'ROLLBACK_TO', defaultValue: '',
               description: 'A version already built, for example 1.0.12')
    }

    stages {
        stage('Check the image') {
            steps {
                bat "docker image inspect calc-web:${params.ROLLBACK_TO} >nul"
            }
        }
        stage('Rollback production') {
            steps {
                input message: "Put calc-web:${params.ROLLBACK_TO} back in production?", ok: 'Rollback'
                bat 'docker rm -f calc-prod 2>nul & exit /b 0'
                bat "docker run -d --name calc-prod -p 8082:8080 calc-web:${params.ROLLBACK_TO}"
                echo "Production is back to version ${params.ROLLBACK_TO}"
            }
        }
    }
}
  1. Deploy two versions to production with calc-web (DEPLOY_ENV = production, twice). http://localhost:8082 shows the newest one.
  2. Run calc-web-rollback with ROLLBACK_TO = the previous version (docker images calc-web lists them). Approve.
  3. Refresh http://localhost:8082: production is back to the old version, in seconds.
  4. Try a version that does not exist, like 9.9.9: the first stage fails before touching production.

This is why artifacts are versioned and kept: a rollback is just a deployment of an older artifact. Next chapter: deployment strategies (blue-green, canary) make it even safer.

🤔 Think: why does the rollback job not need docker build? What would make a rollback impossible?
