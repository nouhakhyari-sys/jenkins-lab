Lab 5 · Deploy with Docker

4. Build the Docker Image

🎯 Why this step? This is the release step of the chapter: the code becomes a versioned artifact. With Docker, the artifact is no longer only a jar, it is an image that contains the jar and Java: it will run the same way in staging and production (slides Why do you need docker?).

Edit your job (Configure) and make two changes.

Step 1: a version for each build

Add this environment block just after the parameters { } block:

Add after parameters { } (Docker and Windows)
    environment {
        IMAGE   = 'calc-web'
        VERSION = "1.0.${BUILD_NUMBER}"
    }

Each build gets its own version: build 12 is 1.0.12. IMAGE and VERSION become variables of the whole pipeline: ${IMAGE} and ${VERSION} in any stage.

Step 2: the Docker image stage

Add this stage after Package, inside stages { }. ✍️ Your turn: the docker build line has three blanks.

Docker image stage, to complete (Jenkins in Docker)
        stage('Docker image') {
            when {
                expression { currentBuild.currentResult == 'SUCCESS' }
            }
            steps {
                dir('app/lab5/calc-web') {
                    // fill in the 3 blanks: image name, tag, build context
                    sh "docker build --build-arg APP_VERSION=${VERSION} -t ____:____ ____"
                }
                sh "echo ${IMAGE}:${VERSION} > image.txt"
                archiveArtifacts artifacts: 'image.txt'
            }
        }
Docker image stage, to complete (Jenkins on Windows)
        stage('Docker image') {
            when {
                expression { currentBuild.currentResult == 'SUCCESS' }
            }
            steps {
                dir('app/lab5/calc-web') {
                    // fill in the 3 blanks: image name, tag, build context
                    bat "docker build --build-arg APP_VERSION=${VERSION} -t ____:____ ____"
                }
                bat "echo ${IMAGE}:${VERSION}> image.txt"
                archiveArtifacts artifacts: 'image.txt'
            }
        }
✍️ The three blanks of docker build … -t NAME:TAG CONTEXT:
  1. Name: the image name, already in a variable of the environment block.
  2. Tag: the version of this build, also a variable.
  3. Context: the folder Docker reads the Dockerfile and the jar from. We are already inside dir('app/lab5/calc-web'), so it is the current folder: one character.
Show the solution

The line becomes:

docker build --build-arg APP_VERSION=${VERSION} -t ${IMAGE}:${VERSION} .

Full stage:

        stage('Docker image') {
            when {
                expression { currentBuild.currentResult == 'SUCCESS' }
            }
            steps {
                dir('app/lab5/calc-web') {
                    sh "docker build --build-arg APP_VERSION=${VERSION} -t ${IMAGE}:${VERSION} ."
                }
                sh "echo ${IMAGE}:${VERSION} > image.txt"
                archiveArtifacts artifacts: 'image.txt'
            }
        }

Windows: the same with bat, as in the box above.

The other lines:

  • when { expression { currentBuild.currentResult == 'SUCCESS' } }: the stage runs only if the build is still green.
  • --build-arg APP_VERSION=…: gives the version to the ARG of the Dockerfile.
  • image.txt: a small text file with the image reference, archived with the jar. The build page now lists the jar, image.txt and the two test reports.
🔮 Predict first. Write your answer down before you run, then compare.
  1. After two runs, how many calc-web images will docker images calc-web list, and with which tags?
  2. With SIMULATE_BUG ticked: will the Docker image stage run? Which line decides?

Run and check

  1. Run the job without the bug. The stage Docker image appears and turns green. The build page lists four artifacts: the jar, image.txt and the two XML test reports.
  2. Find your image. Jenkins does not keep it: docker build sent it to the Docker engine of your computer. Two ways to see it:
    • Docker Desktop › Images: find calc-web with the tag of your build (build 6 → 1.0.6). The list does not always refresh by itself: click the circular arrow next to Last refresh. Still empty? Use the terminal.
    • Terminal (PowerShell, or the Terminal button of Docker Desktop): docker images calc-web. The terminal always shows the current state.
  3. Watch the version go up. Run the job again, without the bug, and list the images again: a second line appears, with the new build number (1.0.6 then 1.0.7). The old image is still there.
  4. Run it with SIMULATE_BUG. Compare with your predictions. Then list the images: is there a new tag?
Terminal: list the calc-web images
docker images calc-web

Example after builds 6 and 7 (sizes depend on your computer):

What you should see
IMAGE            ID             DISK USAGE   CONTENT SIZE   EXTRA
calc-web:1.0.7   7f3b9c2e41aa       457MB          116MB
calc-web:1.0.6   2ac4525dd606       457MB          116MB

How to read it: IMAGE = name:tag, the tag being 1.0. + the build number. EXTRA shows U (in use) only when a container runs from the image: none yet, part 5 starts the first one. CONTENT SIZE is the compressed size, the one that is downloaded or pushed to a registry. Older Docker versions show other columns (REPOSITORY TAG IMAGE ID CREATED SIZE): same information, the tag is in its own column.

Show the explanation
  • One image per build: 1.0.12, 1.0.13… Each tag says which build produced it, so you can find its tests and its commit, and redeploy an old one (challenge 3). With latest, every build would overwrite the previous name.
  • The tag follows the build number, not a counter of images. If build 8 is yellow (bug), there is no 1.0.8: the next green build gives 1.0.9. A missing number = a build that was not good enough to become an image.
  • With the bug, the build is yellow, so the when condition is false: the stage is skipped (grey). A build that failed its tests never becomes an image, so it can never be deployed.
💥 Break it on purpose (2 min). In the docker build line, replace the last . by .. (the parent folder) and run. Read the error: Docker looks for the Dockerfile in the context and does not find it. Put the . back.
Screenshots for the hand-in: the build page with its Build Artifacts (artifacts.png), and the terminal with the output of docker images calc-web (docker.png; add the output of part 5 to it later).
✅ Checkpoint 4: answer in report.txt, in your own words (one or two lines each).
  1. Give the tag of your last image. Why use the build number in the tag, and not latest?
  2. With SIMULATE_BUG, was the Docker image stage run? Which line of the Jenkinsfile decides that, and why is it a good rule?
See the answer
  1. The tag looks like calc-web:1.0.N, N = the build number (for example 1.0.11). With the build number, each image is unique and you know which build made it: its tests, its console, its commit. You can redeploy an old one (rollback). With latest, every build overwrites the same name: you never know which version runs, and the old one is gone.
  2. No: the stage was skipped. The line when { expression { currentBuild.currentResult == 'SUCCESS' } } decides it: with failing tests, the build is UNSTABLE (yellow), not SUCCESS. Good rule: a version that failed its tests never becomes an image, so it can never be deployed.
